# 数据包子系统：框架原生的配置表加载规范

## Summary

为 NexusFramework 增加**数据包子系统**：定义内容包四元组（程序包/数据包/资源包/本地化包）中"数据包"的规范与实现。数据包是自包含交付物（表结构 + Luban 生成的强类型程序集 + 表数据 + 包清单），运行时经框架注册 API 统一接入 `TableModel`（表→Model 存储，实例→Carrier），支持多包（本体/DLC/mod 静态引用模拟）行级覆盖合并，并附骨架模板与一键复制工具，使配置表开发与多包扩展成为框架原生能力。

---

## Problem Frame

当前配置表能力被绑定在 GAS 库内部：GAS 运行时通过自研 `IConfigLoader` 接口 + `ConfigModel` 私有缓存承载所有配置数据，而 Luban 表结构定义、生成的强类型代码与桥接代码全部散落在 Demo 项目层（`Assets/Demo/Table/`、`TableClass/`、生成的 `LubanConfigLoader.cs`）。Core 库（`NexusFramework`）没有任何表加载能力，其他非 GAS 模块若要使用配置表，只能复制 GAS 的私有链路或绕道 Demo。

框架已提供两种运行时数据载体（`DataCarrier`/`DataTrait` 与 `AbstractModel`），但配置数据没有进入这些框架模式——GAS 的 `ConfigModel` 是 GAS 专属形状，无法被框架组件以统一方式获取。

框架 Core 没有任何表加载能力，新项目从零获得配置表能力需要复制 GAS 的私有链路并手工搭建 Luban 加载与合并机制，开发步骤重复且无法复用框架模式。未来游戏形态是"本体 + DLC + mod"共存的同构内容包结构（配置表是其中"数据包"的核心），本子系统先行落地数据包注册、行级合并与规范基石，mod 运行时加载与内容包整体架构属后续范畴（见 Scope Boundaries）。

---

## Actors

- A1. 框架维护者：设计并维护数据包规范与实现（`NexusFramework.Config` 库），提供注册 API 与一键复制工具
- A2. 游戏业务开发者：使用数据包定义业务表，通过框架模式（`GetModel<TableModel>()`）读取配置
- A3. mod 开发者：创建 mod 数据包（Luban 生成强类型程序集），通过框架注册 API 扩展或覆盖本体表
- A4. Demo 验证者：以静态引用模拟多包共存，验证数据包规范的正确性

---

## Key Flows

- F1. 新项目初始化数据包
  - **Trigger:** 项目需要配置表能力，执行数据包初始化工具
  - **Actors:** A2, A1
  - **Steps:** 运行一键复制工具 → 项目 Table 目录获得骨架模板（luban.conf / 表结构 xlsx / gen 脚本）→ 定义业务表结构 → 运行 gen 生成强类型代码与 JSON 数据
  - **Outcome:** 项目拥有符合规范的数据包骨架，可独立编译为强类型程序集
  - **Covered by:** R3, R5, R10

- F2. 运行时加载与行级合并
  - **Trigger:** 游戏启动，Demo 引导代码按优先级加载并注册数据包（内容包加载管线不在本次范围，以静态引用模拟）
  - **Actors:** A2, A1
  - **Steps:** 按优先级（本体→DLC→mod）依次注册数据包 → 各包注册自己的表到框架 → 低优先级先注册、高优先级按主键覆盖/追加行 → 全部进入 `TableModel` 统一存储
  - **Outcome:** 框架组件可通过统一 API 获取合并后的最终表数据，冲突按优先级正确裁决
  - **Covered by:** R6, R7, R8, R9

- F3. 多包扩展配置（DLC/mod，静态引用模拟）
  - **Trigger:** mod 开发者向游戏新增或覆盖配置
  - **Actors:** A3, A2, A4
  - **Steps:** mod 创建自己的数据包（表结构 + gen + 强类型程序集）→ 按流程规范完成程序集依赖处理 → Demo 以静态引用模拟注册接入 → 同表行按优先级覆盖本体数据
  - **Outcome:** mod 新增表可被框架查询，覆盖表按主键生效，本体代码无需改动
  - **Covered by:** R4, R6, R9, R11

## Requirements

**内容包与数据包规范**
- R1. 数据包由四部分组成：表结构定义、Luban 生成的强类型程序集、Luban 导出的表数据、包清单；四部分作为一个自包含交付物分发。
- R2. 数据包清单包含包标识、加载优先级、依赖声明与表清单字段，作为内容包四元组的公共上下文预留。
- R3. 数据包的表结构定义基于 Luban 工具链（xlsx + luban.conf + gen 脚本），数据包规范定义其目录与命名约定。
- R4. 强类型表代码（Luban 生成的表类）生成进各数据包自己的程序集，不进入框架库；各包经 luban.conf 的命名空间配置使用包级唯一命名空间（cfg 仅为 GAS 遗留命名，非 Luban 硬性要求），保证多包共存时类型无歧义；框架库对具体表类型零知识。
- R5. 数据包规范提供流程规范文档，包含：
  - gen 流程标准化说明：gen 脚本可配置、可分 target 生成，生成行为由数据包规范约束而非写死（gen 脚本模板默认零配置开箱即用，配置仅作覆盖项）；
  - 数据包程序集的生成方式与依赖开发流程（程序集加载管理属程序包职责，本规范仅约定流程）；mod 覆盖本体表时，表结构来源于复制本体表结构 xlsx，模板提供校验脚本对比两包 schema 输出差异报告；
  - gen 模板产物包含包注册引导类（静态注册入口，接收本包 Tables、包标识/优先级与本包行数据 JSON 输入），由 gen 脚本模板后处理生成而非手写；启动接入代码亦由模板产物生成，注册触发无需手写加载代码。

**运行时存储与获取**
- R6. 框架提供 `TableModel`（继承 `AbstractModel`），作为所有数据包表的统一运行时存储，表数据按"表→Model"框架模式承载。
- R7. 数据包经注册 API 接入框架：注册时携带包标识与优先级，注册结果进入 `TableModel` 统一存储。
- R8. 框架组件可通过框架模式获取表数据（`GetModel<TableModel>()` 后的泛型表/行查询），与既有 Model 获取链路一致。
- R9. 多包同表采用行级覆盖合并，规则如下：
  - 同表判定：表名一致且列属性一致（列名、列类型、主键字段均不可变）的表自然被视为同一张表；需要新增列的包应新建表而非覆盖；表名相同但列属性不一致的注册被拒绝并给出字段差异诊断。类型名与命名空间仅作程序集内识别，不承载跨包合并键；
  - 合并键提取基于单字段主键约定（键名由模板约定，实测为大写 ID 单键），仅支持单字段主键；
  - 注册按清单声明的优先级排序应用（本体→DLC→mod，低优先级先注册、高优先级按主键覆盖或追加行），同一主键最终只保留最后一条生效数据（含废除行）；同优先级包按注册顺序稳定平局裁决（最后注册者胜）；
  - 参与删除语义的废除列（约定名 is_void，bool 型）由模板默认包含，覆盖同一张表的各包均保留该列；已发布且不含该列的旧包不支持覆盖方删除语义（注册期拒绝并给出诊断）；
  - 注册期以高优先级包行 JSON 试反序列化到已注册表行类型，校验结构兼容（主键/列/废除列一致性），校验失败即拒绝该包注册并输出表名与字段差异诊断；覆盖表不得引入新的多态类型（由反序列化器的 $type 静态分派天然约束）；
  - 合并以已注册表（最低优先级包）的行类型为存储类型，高优先级行经 JSON 重解析（复用已注册表行类型的反序列化器重建）写入；
  - 废除标记按普通字段覆盖规则处理：废除行（is_void=true）写入后该主键视为无合法数据，查询与迭代均不可见；更高优先级包对已废除主键提供新行（is_void=false）即可反转废除；
  - 表中引用（跨表 ref）以原始键存储，查询期在合并后视图上解析，引用目标行缺失时返回默认值并记录警告；引用密集型表不建议稀疏覆盖；
  - 各数据包同构（同为 Luban 生成），均可经注册 API 扩展或覆盖已注册表，框架原生支持。

**生成工具与模板**
- R10. 数据包子系统附带骨架模板资产（luban.conf / 表结构骨架 xlsx / gen 脚本模板）与一键复制工具（含初始化模板入口，一键完成模板复制；模板 gen 脚本默认零配置开箱即用，配置仅作覆盖项），新项目可初始化符合规范的表目录。

**多包扩展与验证**
- R11. Demo 层以静态引用方式模拟本体/DLC/mod 多包共存（mod 仅指同构数据包实例，不含运行时加载/分发，见 Scope Boundaries），验证注册、行级合并与框架获取链路的正确性；合并实现基于约定内省（按约定名反射提取主键/废除字段、枚举表），不依赖编译期泛型类型约束，确保静态引用验证路径与未来运行时程序集加载路径共享同一合并代码（合并代码共享；动态路径的引导类发现契约见规划问题清单）。

## Acceptance Examples

- AE1. **Covers R9, R11.** Given 本体包与高优先级包（mod，静态引用模拟）注册同一张表（主键 1..10），当高优先级包注册包含主键 5..15 的行后，查询主键 5 返回高优先级包行、主键 3 返回本体行、主键 15 返回新增行。
- AE2. **Covers R7, R8.** Given 两个数据包已按优先级注册，当框架组件执行 `GetModel<TableModel>()` 查询任一表的行时，结果与合并规则一致，无需感知数据来源包。
- AE3. **Covers R9.** Given 本体包表行主键 1 有效而高优先级包（mod，静态引用模拟）将该行覆盖为废除标记（is_void=true），当查询主键 1 时结果与行不存在一致（返回默认值，框架层过滤，查询与迭代均不可见）；若更高优先级包再提供主键 1 的新行（is_void=false），查询恢复返回该行（废除可反转）。
- AE4. **Covers R6, R7, R8.** Given 数据包子系统单元测试程序集仅引用 NexusFramework 与 NexusFramework.Config（零 GAS 引用），当执行注册 → 行级合并 → 框架查询全链路测试时，全部通过且测试中不出现 GAS 类型引用——验证非 GAS 模块可获得表加载能力。
- AE5. **Covers R5, R10.** Given 全新空项目（验证载体：独立工程或 Demo 内最小工程，规划阶段确定），当执行一键复制工具（初始化入口）→ 定义一张业务表 → 运行 gen → 框架查询时，端到端可运行且全程无手写加载代码（定性验收）。

## Success Criteria

- 非 GAS 模块（如未来的 Tag 层级、物品、任务）可仅依赖数据包子系统获得表加载能力，无需引入 GAS 库——以零 GAS 引用的完整单元测试（AE4）验证。
- 新项目从零获得配置表能力的成本显著降低（定性验收）：一键复制工具（初始化入口）→ 定义表 → gen → 框架模式读取，全程无手写加载代码。
- 多数据包（本体/DLC/mod，静态引用模拟）可注册、合并并扩展配置（行级覆盖/追加/废除），无需修改本体代码。

## Scope Boundaries

### Deferred for later

- 程序包/资源包/本地化包的实现与内容包整体的发现、加载管线（含程序集运行时加载管理）——本次仅预留包标识/优先级/依赖字段与流程规范。
- mod 运行时程序集加载——本次仅以流程规范（R5）与 Demo 静态引用模拟（R11）覆盖；mod 生态与内容包整体架构不属于本次需求范畴。
- 远程/热更表源（服务器表、AssetBundle 内表）——注册接口预留扩展点，不做实现。
- 非 Luban 表源（手写 JSON / ScriptableObject 表）——mod 采用 Luban 同构方案，暂不提供弱类型通道。
- GAS 库重构（删除私有 `ConfigModel`/`IConfigLoader`、改从 `TableModel` 读取、GAS.Editor 工具链迁出）——作为 Config 库开发完成后的独立测试任务，其验收标准为 GAS asmdef 对 Luban 完全无感知（运行时与 Editor 均不引用 Luban.Runtime）。

### Outside this product's identity

- Luban 工具链本体的分发与管理（Luban.dll 命令行属开发环境依赖，不随框架库分发）。
- mod 的完整生态能力（mod 商店、版本冲突管理、模组 UI）——数据包规范只解决"配置表可扩展"，不定义分发与运营机制。

## Key Decisions

- 数据包自带强类型程序集：Luban 生成的表类型（包级唯一命名空间）进各包自己的程序集，框架库对表类型零知识——保证框架通用性最大化，替代"生成进框架库/项目层"方案。
- 直接包装 Luban（编译期依赖）：新库依赖 Luban.Runtime，换取开箱即用的强类型表访问。
- mod 也用 Luban 同构生成：全链路强类型统一，不做 JSON+schema 弱类型通道，避免双轨复杂度。
- 行级覆盖合并：本体→DLC→mod 默认优先级，主键覆盖/追加，非整表替换——支持"mod 小改数据"的典型场景。
- 表→Model、实例→Carrier：配置是全局只读数据，用 AbstractModel 承载；运行时实例数据（如单位、效果实例）走 DataTrait/Carrier 载体——实例内存模式本就应合理采用 Core 功能，`TableModel` 不承载实例数据（边界声明）。
- 规范+实现+一键复制工具全量落地：不只是规范文档，配套模板资产与一键复制工具，落实"简化开发步骤"目标。
- 程序集加载只做流程规范：Assembly.Load 管理属程序包边界，本次以文档约定生成与依赖开发流程，Demo 静态引用验证。
- 包级命名空间隔离：Luban 支持命名空间配置（cfg 仅为 GAS 遗留命名），数据包规范约定每包表类型放入包级唯一命名空间，消除多包共存时的类型歧义。
- 承诺记录：本库对 Luban 生成形状的依赖清单（生成的表类 API、主键约定、命名空间配置）作为显式假设边界，供未来工具链替换或弱类型需求出现时评估迁移面。

## Dependencies / Assumptions

- Luban UPM 包（`com.code-philosophy.luban`）已通过 manifest.json 安装，提供 `Luban.Runtime` 与 `Luban.Editor` 程序集（已核实）；manifest.json 应钉住 Luban 版本，升级 Luban 时重跑验证集（模板产物 + AE5 回归 + 承诺记录更新）。
- 框架为源码级目录结构（`Assets/NexusFramework`、`Assets/NexusFramework.GAS`），非 UPM 包分发——生成代码入库无分发污染问题，但仍采用"各包自带程序集"方案。
- Luban 命令行工具 `Tools/Luban/Luban.dll` 当前不存在（gen.bat 引用但文件缺失），属开发环境依赖，不影响规范定义与库内实现；AE5 端到端验收前置：下载 Luban CLI（钉版本）到 `Tools/Luban/`，列为规划首项小任务（与库实现并行准备）。
- 测试工程基础设施（AE4 单元测试程序集）为规划交付物，需在仓库中建立测试工程。
- GAS 运行时当前已通过 `IConfigLoader` 解耦（asmdef 零 Luban 引用，已核实），后续 GAS 重构（独立任务）转向依赖数据包子系统时风险可控。

## Outstanding Questions

### Resolve Before Planning

- 无。

### Deferred to Planning

- [Affects R8][Technical] `TableModel` 泛型查询的具体接口形状（按表类型 vs 按表名 + 行类型），以及多包合并后表容器的内部组织方式。
- [Affects R2][Technical] 包清单的文件格式与字段序列化方式（JSON / ScriptableObject / 其他），以及"包标识/优先级/依赖"的取值约束。
- [Affects R4][Technical] 注册 API 与各包生成代码之间的约定接口形状（包级命名空间 + 包注册入口的衔接方式）；注册契约携带本包行数据 JSON 输入与清单优先级——规划阶段必决项。
- [Affects R9][Technical] 主键约定实测（键名/类型/单字段限制，Demo 现状为大写 ID 单键）——规划前置任务，确认后固化到模板约定。
- [Affects R6][Technical] 默认表数据源与默认 loader（如 Resources 目录约定），兑现"全程无手写加载代码"。
- [Affects R11][Needs research] 数据包程序集的编译产物形式（独立 asmdef 目录 vs 预编译 dll）与 Demo 静态引用模拟的具体做法。
- [Affects R11][Technical] 动态加载路径的引导类发现契约（约定类型名/方法签名，供 Assembly.Load 后反射调用）。
- [Affects R5][Technical] 包注册引导类与启动接入代码的生成载体：gen 脚本模板后处理（方向已定，规划落实）。
- [Affects R10][Technical] 一键复制工具的调用入口（Editor 菜单或命令行）。
- [Affects AE4][Technical] 测试工程基础设施（单元测试程序集交付物）。
- [Affects AE5][Technical] AE5 验证载体（独立工程 vs Demo 内最小工程）。
- [GAS 重构任务][Technical] GAS 重构的过渡策略（一次性删除旧接口 vs 短期双实现）与 Demo 程序化注册（`DemoConfigLoader`）的替换方式，作为后续独立任务的规划输入。
