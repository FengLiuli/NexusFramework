# 内容包模型：开题与结论

> **本文已完成收口。** 开题阶段的三个疑点与 D1–D8 决策点已全部有结论（§五）。
> 正式需求待编写为 `R008`；数据包子集已在 [R006](../requirements/R006-data-pack-config.md) 定稿。

---

## 一、模型总览

```text
框架库（NexusFramework / Config / Inventory …）—— 提供机制，不是内容包
        ▲  经契约包被依赖
交付单元（Bundle）= 分发 / 安装单位：一个目录 / zip / Workshop item
  core（本体）· dlc.* · mod.*
  └── 内容包 ×1..N（每个有自己的清单：packId / priority / subPacks）
        ├── 程序包（可选）  NF 组件实现：注册或替换服务（ICombatService 等）
        ├── 数据包（可选）  表行数据（Luban 导出的 JSON）
        ├── 资源包（可选）  资产
        └── 本地化包（可选）key → 文本
              │  各自负责加载，运行时经 game API 注册
              ▼
运行时容器：服务注册表 / TableModel / 资源表 / 本地化表（合并后视图）
```

三条结构性约定：

1. **交付单元是分发单位，内容包是注册单位**——一个交付单元包含一个或多个内容包，每个内容包用清单表述自身内容（C2）；
2. **程序集不是分类**——程序集属于交付单元，其中的内容包共享（C3）；任何内容包都携带程序集，不影响其子包构成；
3. **契约包在四元组之外**——它是所有内容包的外部依赖，有自己的版本号与兼容期，不随任何内容包分发；**游戏本体是优先级最低的内容包**（C8），框架库本身不是内容包。

---

## 二、结论

### C1. 四元组保留为"品类分类"

程序 / 数据 / 资源 / 本地化四类内容在职责上正交，作为**内容包的组成分类**成立。但它不是包的划分单位——一个 DLC 是一个内容包，内部可同时具备四类内容；一个纯翻译包只有一个本地化子包。

### C2. 内容包是注册与启用单位；交付单元可以包含多个内容包

两个层级，职责不同：

| 层 | 名称 | 职责 | 标识 |
|---|---|---|---|
| **分发** | 交付单元（Bundle） | 下载、安装、版本与更新：一个目录 / zip / Workshop item | `bundleId` |
| **运行** | 内容包（Content Pack） | 注册、启用 / 禁用、优先级、依赖校验 | `packId` |

一个交付单元包含 **1..N 个内容包**，每个内容包用**自己的清单**表述自身内容（`packId`、`priority`、`subPacks`、`targets`、依赖）。交付单元只有一份"容器清单"，声明包标识、版本、更新源与内含内容包列表。

需要分层的典型场景：

- **主功能包 + 自带翻译**：`com.acme.overhaul` 内含主包与 `com.acme.overhaul.zh-cn`，翻译可以用 targets 精确指向主包（C7）；
- **兼容补丁**：一个 mod 附带针对某其他 mod 的兼容包，用户可单独启用 / 禁用而不影响主包；
- **共享程序集**：多个内容包共用一份程序集，避免重复编译与重复加载（C3）。

优先级作用于内容包，不作用于交付单元；子包继承所属内容包的优先级。**启用粒度是内容包**，不是交付单元——用户可以在一个交付单元内只启用兼容补丁。

### C3. 程序集属于交付单元，不是内容包

一个交付单元编译出**一组程序集**，其中的内容包共享：注册入口按内容包划分，但类型定义、加载器实现、服务实现可被多个内容包共用。因此"有没有程序集"不能用来区分包的类型。

Luban 实测补充：跨程序集的行类型不可互操作（同名 `Type` 不相等、同命名空间编译冲突），所以**行类型只由本体提供**，内容包不携带自己的表行类型副本；数据以行 JSON 提交。

运行期含义：**程序集按交付单元加载/卸载，内容包按清单启用/禁用**。禁用一个内容包不会卸载它的程序集，只是不注册、不合并其内容——这决定了"禁用程序包"的语义是"不注册它的服务实现"，而不是"把代码从内存移除"。

### C4. 程序包 = 内容包提供的 NF 组件

程序包不是"代码包"，而是**行为注入**：内容包实现核心定义的接口（如 `ICombatService`），在注册阶段替换或扩展核心的默认实现，从而运行自己的程序逻辑。

```text
核心定义接口（契约包）→ 核心默认实现 → 内容包实现（按优先级注册覆盖）
```

这要求把服务分成三类，并在契约中显式声明：

| 类别 | 语义 | 冲突处理 |
|---|---|---|
| **可覆盖**（Override） | 内容包替换核心默认实现 | 只能一个生效；优先级高者胜；同级冲突拒绝并诊断 |
| **可扩展**（Extension） | 内容包追加实现，核心多播 | 全部保留，按优先级排序执行 |
| **核心保留**（Core-only） | 不可替换（CarrierManager、事件总线、时间服务等） | 注册即拒绝并诊断 |

### C5. 契约包是所有内容包的外部依赖

SDK 内容：`NexusFramework`、`NexusFramework.Config`、`NexusFramework.Inventory`、`Game.Api`、Luban Runtime、模板与校验工具。

- 契约包只含接口、只读值类型、事件 struct、约定常量与稳定查询入口；**不含 Luban 行类型**；
- 独立**契约版本号**；内容包清单声明依赖范围；注册时校验，不满足拒绝；
- 破坏性变更（删改接口/事件字段）升主版本并保留过渡期；
- 服务接口是最高价值的契约：签名与行为语义变更都属于破坏性变更。

### C6. 加载能力在框架，加载选择在内容包

- 能力：`NexusFramework.Config` 提供数据源抽象与内置实现（Resources / File / Addressables / Memory）；
- 选择：内容包在注册时提供自己的 source 实例，或选择内置实现；清单中声明 `source` 与根路径；
- 合并：核心只做合并、查询与诊断，不规定数据存放位置；
- 扩展：内容包可自行实现接口（如加密包、远程热更源），不改核心代码。

资源包与本地化包遵循同一分层：底层"按路径取字节"的源实现可复用，领域接口各自解析（`IDataPackDataSource` → `JSONNode`，本地化源 → 文本表，资源源 → 资源引用）。

### C7. 本地化包：按内容包分链、多语言宽表

本地化包的形态接近资源包（都是 key → 内容），但 **key 空间不属于自己**——这是"第三方为其他内容包提供翻译"的前提。因此它的选择与合并**不能按全局一张表**处理，而要按内容包分链。

**组织单位：按支持的内容包分子包，不按语言分。**

```text
本地化子包 = targets（精确 packId 列表）+ 一张多语言宽表 + priority
```

理由：新增内容包是常态，新增语言是罕见事件。按 target 分子包时，新增内容包只需增加一个文件，不触碰既有文件；按语言分则相反——每加一个 target 都要在所有语言子包里改一遍。

**表结构（一表多语言）**：

```text
ID                | en              | zh_cn        | ja
core:item.potion  | Healing Potion  | 治疗药水      | 回復薬
core:ui.confirm   | Confirm         | 确认          | 確認
```

- 列名即语言，映射规则为 `_` ↔ `-`（`zh_cn` ↔ `zh-CN`），映射写在子包声明中，不做隐式猜测；
- 新增语言 = 加一列（Luban schema 变更，罕见且影响面限于本子包）；
- 空单元格 = 未翻译，走回退；"故意为空"需要显式标记（待决）。

**声明**：

```text
targets      支持的内容包：packId 精确列表（如 ["core"]、["core", "com.acme.qol"]）
table        多语言宽表的表名
columns      列名 → 语言标签映射（zh_cn → zh-CN）
priority     同一 target 内的排序权重
```

`targets` 只做精确匹配，不设前缀通配：通用 UI 与系统文本属于 `core` 内容包（C8），第三方翻译声明 `["core"]` 即覆盖。

**选择流程**（设置界面）：

1. 选择语言；
2. 选择启用的内容包；
3. 为每个启用内容包安排本地化子包排序（默认按 `priority`，用户可调整）。

**查找**（对内容包 P 的 key K，语言 L）：

```text
chain(P) = 声明支持 P 的本地化子包，按排序从高到低
for pack in chain(P):
    if pack 的表含 K 行，且 K 在语言 L 的列非空 → 返回
if L != 默认语言:
    依次尝试上位语言（zh-CN → zh），最后默认语言，重复上面的链
返回 key 原文（Editor 显示 key；发布期显示占位符并记录缺失）
```

**四条实现约束**：

- **逐包回退是语义，不是运行时成本**：加载/切换时把每个 `(内容包, 语言)` 的链预合并成一张字典（按排序覆盖），运行时 O(1)；一个宽表子包在合并时被拆成多个语言条目；语言或内容包启用状态变化时重建；
- **不做目标存在性校验**：翻译可以先于内容包发布；启动后输出"孤儿 key 报告"（子包有该行、目标包无该键），只告警不拒绝；
- **支持为空但不阻断**：一个内容包没有任何本地化子包时，全部 key 走默认语言 / 原文，不视为错误；
- **覆盖率按列统计**：每个子包按语言列计算非空比例，供翻译工作流使用。

**边界**：

- 多个本地化子包可同时服务同一个内容包（官方基础 → 社区补丁 → 单条修正），排序决定优先级；
- 一个子包可同时服务多个内容包（出现在多条链中）；
- 本地化包自身也是内容包，其启用状态独立于 target 的启用状态；target 全部禁用时该链为空；
- 本地化包通常只包含本地化子包，不携带数据包 / 程序包。

> 正式需求：[R009 Localization](../requirements/R009-localization.md)（核心）与 [R010 LocalizationForConfig](../requirements/R010-localization-for-config.md)（宽表适配）。

### C8. 游戏本体是最基础的内容包

游戏本体不再作为"特殊核心"存在，而是记为 `core` 内容包：

| 维度 | core 内容包 |
|---|---|
| packId | `core`（保留标识，第三方不得使用） |
| 优先级 | `Base = 0`，所有其他内容包在其上叠加 |
| 子包 | 基础表（数据包）、基础资源（资源包）、基础语言文本（本地化包）、默认服务实现（程序包） |
| 加载顺序 | 最先加载、最先注册；其他内容包按优先级递增 |

三条推论：

1. **框架库与 core 内容包分离**：`NexusFramework` / `Config` / `Inventory` 提供机制（表存储、合并、索引、事件），它们不属于任何内容包，且必须先于所有内容包就绪；`core` 是"用这些机制组织起来的第一份内容"。
2. **不为 core 写特例分支**：core 与其他内容包走同一套加载、注册、合并路径，只是优先级最低。任何"if (packId == core)"的代码都意味着模型有漏洞。
3. **本地化回退对 core 与 mod 语义一致**：core 的本地化包提供默认语言文本；其他内容包应自带自己的默认语言文本（或直接以 key 原文显示）。这样"回退到默认语言"不必为 core 开一条特殊路径。

### C9. 架构定位：词汇在核心，编排是可选库

内容包模型的定位不是"核心 or 扩展"的二选一，而是三层：

| 层 | 内容 | 是否可选 |
|---|---|---|
| **Core 原语** | 包标识（`ContentPackId` 字符串值类型）、优先级（int）、注册结果与诊断类型 | 必须 |
| **能力库** | Config / Assets / Localization / Inventory 的"带来源标识的注册与合并" API | 按需引用 |
| **编排库** `NexusFramework.ContentPacks` | 清单、发现、加载、生命周期四阶段、契约版本校验、服务覆盖裁决、本地化链 | 可选（产品默认启用） |

三条理由：

1. **词汇必须在下层**：Config 与 Inventory 的 API 都需要"来源标识 + 优先级"作为参数。若这些类型定义在编排库，就会形成"核心依赖扩展"的倒挂。
2. **编排不应进 Core**：单机项目不需要 DLC/mod；若 Core 知道"包"，所有 API 都要以包为维度，不使用该功能的项目要付认知成本。编排是策略，不是机制。
3. **依赖方向是编排 → 能力库**：编排层调用各子系统的注册 API，不反向。它只决定**顺序与裁决**，不重新实现合并。

一条硬边界：**合并语义、索引维护、事件分发必须留在能力库**。编排层若自行合并数据，会绕过 `TableModel` 的废除行过滤与索引一致性，迟早分裂成两套实现。

产品口径：本项目的定位是"本体 + DLC + mod 同构"，因此 `ContentPacks` 作为标准依赖随游戏发行；但技术上移除它后，Config 与 Inventory 仍可独立工作（单包模式），这是分层是否正确的检验标准。

### C10. 能力库清单

四元组对应四个能力面，但只有三个需要独立库——程序包复用 Core 的 IOC，不新建库。

| 能力面 | 库 | 现状 | 最小职责 |
|---|---|---|---|
| 数据包 | `NexusFramework.Config` | 需求定稿（R006），零代码 | 表的注册、合并、查询、加载抽象 |
| 资源包 | `NexusFramework.Assets` | **未建** | 资源键注册、按内容包管理生命周期、加载策略注入、配置引用校验 |
| 本地化包 | [`NexusFramework.Localization`](../requirements/R009-localization.md) + [`LocalizationForConfig`](../requirements/R010-localization-for-config.md) | 需求定稿（R009/R010），零代码 | 核心：语言、文本注册、按内容包分链合并、回退、缺失报告；适配器：多语言宽表 → 注册条目、key 与覆盖率校验 |
| 程序包 | Core 的 IOC（扩展） | IOC 已落地 | 带来源与优先级的注册、可覆盖/可扩展/核心保留三分类、冲突诊断 |
| 编排 | `NexusFramework.ContentPacks` | **未建** | 清单、发现、四阶段生命周期、契约版本校验、失败隔离与汇总 |

```text
ContentPacks（编排，可选）
   ├── NexusFramework.Config
   ├── NexusFramework.Assets
   ├── NexusFramework.Localization
   └── NexusFramework（IOC 注册元数据）
Inventory / GAS —— 内容包的使用者，不参与编排
```

三项不新建的理由：

1. **程序包不需要库**：服务覆盖就是 IOC 的注册顺序与覆盖语义；只需要给 IOC 补注册元数据（来源、优先级、类别）与冲突诊断，不需要新程序集。
2. **契约包不是运行时库**：它是构建产物（DLL 快照 + 模板 + 校验脚本），由发版脚本生成，不被任何运行时程序集引用。
3. **内容发现属于编排**：从目录、Addressables 或内置列表读取 manifest，是编排库的职责，不值得单独成库。

两个新库都应保持**薄**：`Assets` 不重造 Addressables 管线，`Localization` 不重造 Unity Localization 的资产体系——它们只提供"按内容包注册、按命名空间解析、按优先级合并"这三件事，底层加载策略可注入。

## 三、交付通道与平台约束

内容包的**程序集如何进入构建**有三种方式，与"包内有哪些子包"无关：

| 通道 | 程序集进入方式 | 平台 | 典型场景 |
|---|---|---|---|
| **A 纯数据** | 不进入（只交 JSON） | 全平台 | 数值调整、翻译、纯数据 mod |
| **B 编译期** | 随游戏构建一起编译/打包 | 全平台 | DLC、官方内容、随包发行的社区内容 |
| **C 运行期** | 运行时加载 | **仅 Mono / 桌面** | 用户自装的代码 mod |

IL2CPP 只能 AOT，运行期无法加载新程序集——通道 C 在 IL2CPP 平台**不存在**，不是性能问题而是能力缺失。目标平台矩阵必须显式声明。

> 注意：通道 A 的内容包也**有**程序集（注册入口与加载器实现），只是它不随包分发；A 指"不交付代码"。

## 四、依赖与注册顺序

```text
契约包（SDK）
   ▲ 编译期
内容包（程序包 / 数据包 / 资源包 / 本地化包）
   │ 运行期注册
   ▼
游戏核心：服务注册表、TableModel、资源注册表、本地化表
   │ 全部注册完成后
   ▼
引用解析（ITableView）→ 服务启动 → 游戏进入可交互状态
```

阶段划分（R008 需固化为需求）：

0. **发现阶段**：扫描交付单元 → 读容器清单 → 枚举其每个内容包的清单 → 构建"待启用集合"（校验 `packId` 唯一、契约版本、包间依赖）；
1. **加载阶段**：按交付单元加载程序集；各内容包加载自己的子包内容（互不依赖）；
2. **注册阶段**：按优先级注册服务、表、资源、文本；同契约覆盖按 C4 裁决；
3. **解析阶段**：跨表引用、本地化 key、资源引用统一在合并后视图上解析；
4. **启动阶段**：调用各服务的初始化钩子，失败隔离并汇总报告。

程序集按交付单元加载，内容包按清单启用——**同一交付单元内只启用部分内容包是合法状态**，未启用的包不注册、不合并，但其程序集仍在内存中。

任何"在注册阶段读取尚未注册的表/服务"的行为都属于时序错误，应被诊断拦截。

## 五、D1–D8 的答案

| # | 开题候选 | 结论 |
|---|---|---|
| D1 | 保留四元 / 三分 / 二分 | **保留品类四分**；但包的单位是内容包（C1/C2） |
| D2 | 优先级与品类 | 正交；优先级作用于内容包，子包继承（C2） |
| D3 | 本地化是否独立 | 独立成子包；不与资源包合并（因为要跨包提供翻译，C7） |
| D4 | 依赖图方向 | 契约包在最底层；内容包依赖契约；资源/本地化是运行期解析依赖，不是编译依赖 |
| D5 | 清单公共字段 | packId、priority、contractVersion、deliveryForm、subPacks、dependencies、source 声明 |
| D6 | 程序包的特殊位置 | 不是包的一种，是"提供 NF 组件"的子包；受服务分类与平台矩阵约束（C4/C5） |
| D7 | 与 Unity 映射 | 数据包 ↔ Config；程序包 ↔ asmdef/DLL + SDK；资源包 ↔ Addressables；本地化 ↔ 独立文本表 |
| D8 | 实例概念 | 两个层级：交付单元（1..N 内容包）+ 每个内容包自己的清单；启用以内容包为单位（C2） |

## 六、行业对比（保留为判断依据）

| 体系 | 代码 | 数据 | 资源 | 本地化 | 包载体 |
|---|---|---|---|---|---|
| Minecraft (Java) | mod 程序集 | data pack | resource pack | 在 resource pack 内 | 独立目录，`namespace:path` |
| Unreal | 插件 .uplugin | DataTable | Pak/Chunk | .locres | chunk 是下载单位，插件是代码单位 |
| Unity | asmdef / UPM | ScriptableObject / 表 | Addressables | Localization | 无统一"包"概念 |
| RimWorld | DLL mod | XML 定义 | 纹理/声音 | 可选翻译 mod | 三件套 |
| Steam Workshop | — | — | — | — | 元数据 + RequiredItems 依赖 |

三条仍然有效的观察：

1. **代码与其他内容分离是共识**，但分离的维度是"加载方式"而非"品类"——UE 的 chunk 可混合四类内容；
2. **本地化独立成包罕见**；我们独立的原因不是分发，而是"翻译可指向其他包"（C7）；
3. **包元数据在 mod 平台最成熟**：标识、版本、依赖声明，与我们的清单字段对应。

## 七、待转 R008 的未决项

1. 发现与生命周期五阶段（含发现阶段）的具体接口与失败语义；
2. 服务可覆盖白名单的初始范围，以及装饰/包装（`Wrap(inner)`）是否本期支持；
3. 同级覆盖冲突的裁决细节与诊断文本格式；
4. **两层清单的 schema**：交付单元容器清单（`bundleId`、版本、更新源、内含包列表）与内容包清单（`packId`、优先级、子包、targets、依赖）；两者的版本字段与依赖声明格式；
5. 资源包与 Addressables 的映射粒度（group / label / catalog）；
6. 本地化包的落地细节：同 target 多包的默认排序、预合并表的构建时机与内存、语言热切换的重建成本、缺失条目的报告格式、受支持的 BCP 47 标签子集；
7. 内容包签名与信任模型（代码包允许执行任意逻辑，是否需要签名校验）；
8. 平台矩阵的产品口径：哪些平台发布时声明支持运行时 mod；
9. **部分启用**：同一交付单元内只启用部分包时，程序集加载、依赖校验（包依赖包、包依赖 bundle）与诊断的规则。
