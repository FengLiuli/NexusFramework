# 会议开题：内容包四元组（程序包/数据包/资源包/本地化包）

## 0. 会议信息

- **主题**：内容包四元组划分的模式合理性论证，以及与成熟游戏内容交付模式的对比
- **目标产出**：①对"四元组"划分的成立性结论（保留/调整/重构）；②四元组公共上下文（包清单字段）的定稿依据；③新会话实施方向（数据包先行已定，其余三包如何规划）
- **前置材料**：`docs/brainstorms/2026-08-01-data-pack-requirements.md`（数据包需求文档，三轮审查闭环）
- **本次不讨论**：数据包内部的合并规则细节（已定稿）；具体 API 形状

## 1. 背景速览

数据包子系统需求文档（三轮审查闭环）中，内容包四元组被定义为**数据包**（表结构 + 强类型程序集 + 表数据 + 包清单）的上级框架：

> 内容包四元组 = 程序包 / 数据包 / 资源包 / 本地化包

现状：

| 包类型 | 当前状态 | 出处 |
|--------|---------|------|
| 数据包 | 规范已定稿（R1-R11），先行落地 | 需求文档全文 |
| 程序包 | 仅预留：清单字段 + "程序集加载管理属程序包职责"边界声明 | R2、R5、Scope Boundaries |
| 资源包 | 仅预留：清单字段 | R2、Scope Boundaries |
| 本地化包 | 仅预留：清单字段 | R2、Scope Boundaries |
| 内容包整体 | 发现/加载管线 deferred（含程序集运行时加载管理） | Scope Boundaries |

**关键事实**：四元组划分在需求文档中**只被引用、从未被论证**——它是讨论"数据包"时引入的背景框架，本身没有经过模式合理性检验。本次会议就是补上这一课。

## 2. 议题一：四元组划分的模式合理性

### 2.1 划分维度是什么？

当前隐含的划分维度是**内容品类**（代码 / 表格数据 / 美术资源 / 语言文本）。需要检验：

- **正交性**：四个品类是否真的互斥且完备？
  - 本地化包是不是资源包的子集？（语言文本本质是文本资产，Minecraft 就把它放在 resource pack 里）
  - 程序包是否天然"包含"数据与资源依赖？（代码引用的表 schema、prefab 引用资源）
  - 有没有第五元？（音频包、关卡包、DLC 故事包……）
- **被替代的划分维度**：为什么不用以下维度？
  - **交付与更新维度**：本体（base）/ DLC / mod（优先级从低到高）——这是运行时语义维度
  - **加载生命周期**：启动加载 / 按需加载 / 流式加载
  - **维护团队维度**：程序 / 策划 / 美术 / 本地化各自负责的包

### 2.2 四元组想解决的问题

候选动机，请逐条检验是否成立：

1. **独立分发与更新**：四类内容热更频率与渠道不同（配置天天改、美术随版本、代码最少动、翻译按语言发行），独立成包可各自更新；
2. **独立责任边界**：不同团队/供应商维护（外包美术、本地化公司）；
3. **平台差异**：本地化需要按语言区隔（德语包/日语包），资源包需要按平台/画质分级（PC 高清 vs 移动端）；
4. **mod 生态**：mod 可只带数据（修改数值）或只带翻译，无需重做资源。

### 2.3 需要论证的疑点（预判）

- **本地化独立成包 vs 并入资源包**：独立的价值（按语言分发、无冗余）vs 成本（多一层清单与合并逻辑）；
- **程序包的特殊性**：代码包无法像数据/资源一样"合并"，只能共存（加载全部或互斥？），且涉及程序集加载/安全边界——它与其他三元不在同一个抽象层上；
- **四元组是"品类分类法"还是"实例分类法"**：一个 DLC 交付物往往同时含四类内容，四元组究竟是"包的四个槽位"还是"每个交付物都要拆成四份"？

## 3. 议题二：成熟模式对比

### 3.1 横向对比表

| 体系 | 程序/代码 | 数据/配置 | 资源/资产 | 本地化 | 包载体与机制 |
|------|-----------|-----------|-----------|--------|--------------|
| **Minecraft (Java)** | mod 独立程序集（Forge/Fabric） | data pack（配方/进度/函数，纯 JSON 数据） | resource pack（纹理/模型/声音/**语言文件**） | 语言文件在 resource pack 内 | 独立目录分发，服务端/客户端分装 |
| **Unreal Engine** | 插件 .uplugin（代码） | DataTable/DataAsset（引擎内资产） | Pak/Chunk 资产体系（.pak 按 chunk 划分，DLC 下载粒度） | .locres 本地化文件 | Chunk 是下载/安装单位，插件是代码单位，二者分离 |
| **Unity (Addressables)** | asmdef/UPM 包 | ScriptableObject/表 | Addressable Groups（catalog + remote content update） | Localization 包（表格驱动） | 资源按 group/label 分组，远程 catalog 驱动更新；无统一"包"概念 |
| **国内手游惯例** | Lua 热更 / HybridCLR | 配置表热更（Luban/JSON） | AssetBundle/Addressables 远程资源 | 语言包内嵌或独立下载 | 三通道热更管线，各管各的 |
| **Bethesda (Skyrim)** | 插件 .esm/.esp（代码+数据混合） | （同上） | .bsa 资源包 | 内嵌语言字段 | 数据/资源二分 |
| **WoW Addon** | Lua 代码（toc 声明） | 配置/表 | 纹理/声音 | 按 locale 目录组织语言文件 | 三合一但本地化按 locale 分目录 |
| **RimWorld/Cities** | DLL mod | XML/定义 | 纹理/声音 | 语言文件（可选翻译 mod） | 社区惯例"程序集+内容+翻译"三件套 |
| **Steam Workshop / mod.io** | —（托管任意文件） | — | — | — | 元数据（标题/描述/预览）、版本、**RequiredItems 依赖声明** |

### 3.2 观察与趋势

1. **代码与其他内容分离是共识**：所有体系都把代码（程序集/插件/Lua）与内容（数据/资源）分开——程序包的独立性成立；
2. **数据与资源是否分离，行业分成两派**：Minecraft 明确分离（data pack vs resource pack），Bethesda 半混合（esp 内嵌数据 + bsa 资源），UE/Unity 不强制分离（都是资产）；
3. **本地化独立成包在行业主流中罕见**：Minecraft/WoW 都把它放进资源包，仅国内手游常做独立语言包下载（渠道/合规需求，而非模式需要）；
4. **"包"的统一元数据在 mod 平台（Steam/modb.io）最成熟**：标题/版本/依赖（RequiredItems）/预览图，恰好对应我们预留的包标识/优先级/依赖字段；
5. **划分维度的业界答案偏向"下载/安装单位"（Chunk、Addressable Group、资源通道）而非"内容品类"**——UE 的 chunk 可混合含四类内容，Addressables 按内容特性（常驻/热更/平台）分组。

### 3.3 对本框架的映射建议（讨论稿）

- 四元组作为**内容品类分类**可保留，但需补充"实例"概念：一个 DLC = 四个包的组合交付物，而不是一个 DLC 强制拆四包；
- **优先级语义**（本体→DLC→mod）与品类正交：任一品类都有优先级；
- **依赖图方向**（讨论）：程序包依赖数据包（表类型）→ 数据包依赖资源包（表引用资源 id）→ 本地化包依赖数据包（文本 key）？还是本地化包最底层？
- **与 Unity 现有体系的映射**：资源包 ↔ Addressable Group（远程 catalog）；程序包 ↔ asmdef/UPM；数据包 ↔ 本次实现；本地化包 ↔ Localization 表或独立 JSON。

## 4. 议题三：关键决策点清单

| # | 决策点 | 候选选项 | 讨论价值 |
|---|--------|---------|---------|
| D1 | 四元组划分是否成立 | ①保留品类四元组 ②本地化并入资源包（三分）③改为"程序包 + 内容包"二分（内容包内含数据/资源/本地化子类型） | 高——决定公共上下文设计 |
| D2 | 四元组与"本体/DLC/mod"优先级的正交关系 | ①正交（任一品类任意优先级）②优先级仅作用于内容包（程序包另论） | 高——影响包清单字段 |
| D3 | 本地化包独立 vs 并入资源包 | ①独立（按语言分发）②并入资源包（Minecraft 式） | 高 |
| D4 | 包依赖图方向 | 程序→数据→资源→本地化？资源→数据→程序？本地化最底层？ | 中——决定加载顺序 |
| D5 | 包清单公共字段定稿 | 元数据/依赖/优先级/版本/校验 + 各包私有字段 | 中——R2 预留字段的扩写 |
| D6 | 程序包的特殊位置 | 代码共存/互斥语义、程序集加载边界、安全校验（数据包先行方案已声明加载管理 deferred） | 中 |
| D7 | 与 Unity 现有体系映射 | Addressables 即资源包？UPM 即程序包？还是自建统一管线 | 高——决定实现路线 |
| D8 | 内容包"实例"概念 | DLC/mod 作为四包组合的交付单元，包清单是否分层（manifest → 四包） | 中 |
