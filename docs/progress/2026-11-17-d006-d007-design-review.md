# 复核记录：D006 / D007 接口设计审查

> 审查对象：[D006 数据包接口设计](../design/D006-data-pack-interface-design.md)、[D007 物品与存储接口设计](../design/D007-item-storage-interface-design.md)
> 审查方法：逐条契约对照现有代码（`Framework.cs` / `FrameworkArchitecture.cs` / `CarrierManager.cs` / `CarrierIndex.cs` / `CarrierGroupIndex.cs` / Luban 生成产物）与四份性能基线。
> 审查结论只谈接口契约，不评价实现排期。

---

## 结论

**D006 可以进入 Unit 1，但需先修订 4 项（否则示例代码落地即出错）。**
**D007 不能进入 Unit 1：存在 5 项会直接导致运行期数据错误或接口不可实现的问题，必须先改设计再写接口。**

| 文档 | P0（阻塞） | P1（接口缺口/自相矛盾） | P2（准确性/细节） |
|---|---|---|---|
| D006 | 4 | 5 | 4 |
| D007 | 5 | 8 | 6 |

两文档共同的根因只有一类：**接口示例与框架实际注册语义不符**（`IOCContainer` 按静态类型注册）。这一类要一次性改掉，否则照抄示例会得到"注册了但取不到"的静默失败。

## 一、D006 阻塞项

### D006-P0-1 数据源是单例 Utility，多包场景取不到正确数据源

**位置**：[D006 §2.4](../design/D006-data-pack-interface-design.md)、[§四 时序](../design/D006-data-pack-interface-design.md)

**事实**：`IOCContainer` 用 `typeof(T)` 作 key（`FrameworkArchitecture.cs:17-21`），同一类型**只能存在一个实例**（后注册者覆盖先注册者，无告警）。而设计里：

- `IDataPackDataSource` 被定义为 Utility（全局单例）；
- `ResourcesDataPackDataSource` 的**构造函数绑定一个 `packId`**；
- `RegisterDataPack(entry, dataSource = null)` 在 `null` 时回落 `GetUtility<IDataPackDataSource>()`。

三者组合的后果：注册 `core` 与 `dlc` 两个包时，全局只有一个 data source，后注册的包会读到**前一个包的数据目录**；若两个包都依赖回落路径，其中一个必然读错。

**建议**（二选一，推荐 A）：

- **A**：`Load` 携带包标识——
  ```csharp
  public interface IDataPackDataSource : IUtility
  {
      Luban.SimpleJSON.JSONNode Load(DataPackId packId, string dataName);
  }
  ```
  默认实现不再在构造时绑定 `packId`，多包共用同一实例。
- **B**：改为工厂 `IDataPackDataSourceFactory.Create(DataPackId)`，`RegisterDataPack` 每次向工厂要实例。

无论哪种，`ResourcesDataPackDataSource` 的 `public DataPackId PackId { get; }` 都应删除或改为方法参数。

### D006-P0-2 注册示例会导致 `GetUtility<IDataPackDataSource>()` 返回 null

**位置**：[D006 §四](../design/D006-data-pack-interface-design.md)（时序图第 4 行）

**事实**：`RegisterUtility<TUtility>(TUtility utility)` 的记录键是**调用时的静态类型**（`FrameworkArchitecture.cs:321-324` → `IOCContainer.Register<T>`）。示例写的是：

```csharp
arch.RegisterUtility(new ResourcesDataPackDataSource(DataPackId.FromString("core")))
```

推断出的 `TUtility` 是 `ResourcesDataPackDataSource`，键即具体类型；随后 `TableModel` 内部 `GetUtility<IDataPackDataSource>()` 查的是接口键 → **返回 null** → 整包注册失败。

**对照**：GAS 的写法之所以正确，是因为 `CreateConfigLoader()` 的返回声明是接口：`protected virtual IConfigLoader CreateConfigLoader()`（`GASArchitecture.cs:19`），所以 `TUtility = IConfigLoader`。

**建议**：示例统一改为显式泛型参数，并在文档里加一句"注册 Utility/Service 必须显式指定接口类型"：

```csharp
arch.RegisterUtility<IDataPackDataSource>(new ResourcesDataPackDataSource(DataPackId.FromString("core")));
```

D007 的 `arch.RegisterService(new ItemService(provider))` 是同一个坑（见 D007-P1-5）。

### D006-P0-3 `Priority` 声明为"决定合并顺序"，但注册 API 无法重排

**位置**：[D006 §2.2 注册语义](../design/D006-data-pack-interface-design.md)

**事实**：文档写"优先级只影响合并顺序：低先注册，高后覆盖；同优先级按注册顺序"。但公开入口只有逐个调用的 `RegisterDataPack(entry, source)`，`TableModel` **在调用当时就合并**，没有任何缓冲/排序能力。若业务先注册 mod（200）、后注册 core（0），结果是 mod 行被 core 覆盖——与 `Priority` 的宣称相反。

**建议**（二选一）：

- **A**：承认现状，改写为"`Priority` 是**声明性元数据**，`RegisterDataPack` 必须由调用方按升序调用；实现侧仅用它做顺序校验与诊断"；
- **B**：补批量入口 `RegisterDataPacks(IReadOnlyList<IDataPackEntry>)`，由 `TableModel` 内部排序后合并。

选 A 更符合 Unit 1 的最小接口目标，但必须把"升序调用"写成调用方契约，否则后续必然出错。

### D006-P0-4 "行级覆盖"的真实语义未声明：整行替换，且必须完整 schema

**位置**：[D006 §2.5 `ITableMerger` / `ITableIntrospector.DeserializeRow`](../design/D006-data-pack-interface-design.md)、[§2.1 `is_void`](../design/D006-data-pack-interface-design.md)

**事实**（对照 `Assets/Demo/Emberheart/GAS/TableClass/unit.cs`）：

1. Luban 行类型是 `sealed partial class`，字段全部 `public readonly`——**实例不可变**；
2. `Deserializeunit(JSONNode)` 对**每一列**做 `IsNumber`/`IsString` 断言，缺列直接抛 `SerializationException`。

由此两条硬约束文档完全没写：

- **覆盖 = 用新行对象整行替换**，不存在"只改几列"。`Merge` 的输入必须是**完整行**；"覆盖方只提供变更列"的直觉实现会抛异常。
- **`is_void` 的反转同样靠整行替换**（AE3 要求"更高优先级包再提供新行即恢复"）。这没问题，但必须在契约里写明，否则实现者会尝试反射写 readonly 字段。

**顺带一个缺口**：包内 JSON **重复主键**。Luban 的 `Tbunit` 用 `_dataMap.Add(...)`（`Tbunit.cs:32`），重复键抛 `ArgumentException`；而 D006 的 `DataPackTableStatus` 没有对应状态（`DeserializeFailed` 语义是"行与类型不兼容"，不是"包内自相矛盾"）。

**建议**：

- 加一节"行合并语义"：整行替换、完整 schema、`is_void` 反转路径；
- 状态枚举补 `DuplicateKey`（或明确并入 `DeserializeFailed` 并在 `Diagnostic` 中给主键值）。

## 三、D007 阻塞项

### D007-P0-1 `item.slot` 索引在无序容器上不成立（会互相驱逐）

**位置**：[D007 §3.1 `ItemLocation`](../design/D007-item-storage-interface-design.md)、[§3.5 索引表](../design/D007-item-storage-interface-design.md)

**事实**：`ItemLocation.SlotIndex == -1` 表示"无序容器"（`ContainerTrait.Kind == Capacity`）。若按 §3.5 对所有物品 `Bind` 到 `CarrierIndex<ItemLocation>("item.slot")`：

- 同一无序容器内**所有物品**的 `ItemLocation` 都是 `{container, -1}`；
- `CarrierIndex` 是双射表，值冲突采用**覆盖驱逐**（`CarrierIndex.cs:66-71`）——后绑定的物品会把前一个物品的条目删掉。

结果：一个装了 100 件药的背包，`item.slot` 里只剩最后 1 件，且 `TryGetCarrier({bag,-1})` 只返回它。

**建议**：

- 明确 `"item.slot"` **只登记 Slot 型容器的物品**；无序容器物品只进 `"item.container"`；
- `Move` / `Split` 的目标为无序容器时必须 `Unbind(SlotLocation)`（若原为槽位型）；
- `IItemQuery.GetLocation(item)` 的实现写成"从 `item.container` 取容器 + 从 `item.slot` 取槽位（无则 -1）"，而不是直接读索引值；
- `ItemLocation` 补 `IEquatable<ItemLocation>` 与 `GetHashCode`（它要作 `Dictionary` 键；默认 `ValueType` 实现走反射，慢且依赖字段顺序）。

**附带**：`CarrierIndex.Bind` 在值冲突时**静默驱逐**，不会通知被驱逐者。`Move` 承诺"目标槽位被占 → 失败"，因此 `ItemService` 必须**先** `TryGetCarrier` 探测再 `Bind`；`Swap` 的两个 `Bind` 也不是原子的（第二个失败时第一个已生效）。这一点文档需要显式写成实现约束，或给 `Swap` 加"预校验全部通过后才写索引"的顺序说明。

### D007-P0-2 容器销毁后 `item.slot` 留下悬垂条目

**位置**：[D007 §3.5 末条](../design/D007-item-storage-interface-design.md)

**事实**：文档写"三张索引均在容器/物品载体销毁时由 `CarrierManager` 自动清理"。逐条核对：

| 索引 | 容器销毁时 | 结论 |
|---|---|---|
| `CarrierGroupIndex<CarrierId> "item.container"` | `TKey == CarrierId` → `RemoveAll(container)` 清整组，并反清成员的账本（`CarrierGroupIndex.cs:139-149`） | ✅ 干净（物品变无归属孤儿，但无悬垂） |
| `CarrierGroupIndex<int> "item.definition"` | 键不是 CarrierId → 不受影响 | ✅ |
| `CarrierIndex<ItemLocation> "item.slot"` | `TValue` 是**含 CarrierId 的复合 struct**，`ValueIsCarrierId` 判定为 false（`CarrierIndex.cs:22`），角色 A 也不命中（容器的 CarrierId 不是该表的 key） | ❌ **该容器的全部槽位条目残留**，`TryGetCarrier(location)` 仍会返回存活物品，且 `location.Container` 指向已销毁容器 |

D005 的引用完整性只覆盖 `TKey/TValue == CarrierId` 的精确类型情形（D005 §2.2.1），复合值类型不在其内——D005 §七 Q5 已把"值谓词"列为 P3，D007 直接踩上。

**建议**（三选一，推荐 A+C）：

- **A**：`ContainerService.Destroy` 内先枚举该容器的物品并逐个 `Unbind` 槽位条目（同时落实 IQ8"禁止销毁非空容器"）；
- **B**：给 `CarrierIndex` 增加可选值谓词 `Func<TValue,bool>`，容器销毁时按谓词清理（回到 D005 Q5，成本较高）；
- **C**：在 `InventoryConventions` 里写明"容器销毁必须先清空"，并由 `Destroy` 的返回值强制（见 D007-P0-3）。

### D007-P0-3 `IContainerService.Destroy` 返回 `void`，无法表达"禁止销毁非空容器"

**位置**：[D007 §3.4](../design/D007-item-storage-interface-design.md)、[IQ8](../design/D007-item-storage-interface-design.md)

**事实**：IQ8 的默认建议是"禁止销毁非空容器；`Destroy` 需先清空或调用 `DestroyWithItems`"，但接口是 `void Destroy(ContainerId)`，且 `DestroyWithItems` 根本不在接口里。调用方无法知道拒绝，也无法选择语义。

**建议**：

```csharp
ItemOperationResult Destroy(ContainerId container);           // 非空 → ContainerNotEmpty
ItemOperationResult DestroyWithItems(ContainerId container);   // 显式丢弃内容
```

`ItemOperationCode` 补 `ContainerNotEmpty`。

### D007-P0-4 `ConfigItemDefinitionProvider` 没有数据来源参数，无法实现

**位置**：[D007 §3.2](../design/D007-item-storage-interface-design.md)

**事实**：构造函数只有三个参数：

```csharp
ConfigItemDefinitionProvider(string tableName,
                             Func<TRow, ItemDefinitionView> map,
                             Func<TRow, int> getId)
```

`TRow` 的行从哪来？没有 `TableModel`、没有 `ITableReader<TRow>`，构造函数里拿不到任何表数据。示例 `new ConfigItemDefinitionProvider<cfg.item>("tbitem", MapItemDefinition, row => row.ID)` 同样缺数据源。

**建议**：加第一个参数并说明取表失败的降级语义：

```csharp
public ConfigItemDefinitionProvider(
    ITableReader<TRow> table,          // 或 TableModel + 在构造时校验表存在
    Func<TRow, ItemDefinitionView> map,
    Func<TRow, int> getId);
```

如果坚持在构造时按表名取，则应接受 `TableModel` 并处理"表未注册"（返回空 provider + 诊断，而不是抛异常）。

### D007-P0-5 存档示例与"不走 `CarrierManager.SaveToFile`"的决策直接矛盾

**位置**：[D007 §五 存档时序](../design/D007-item-storage-interface-design.md) vs [§3.9](../design/D007-item-storage-interface-design.md) / I14

**事实**：§3.9 与 I14 明确"物品存档**不走** `CarrierManager.SaveToFile`，采用容器批量快照"，理由写得很充分（137 B/件 vs 35 B/件）。但 §五 的时序代码仍写着：

```
存档：
  carrierManager.SerializeCarrier(containerCarrier) / SaveToFile(...)
  // 物品库不参与落盘；Serialization 结构由 Trait 决定
```

这段是 D007 之前版本的残留，会直接误导实现者写出逐物品 JSON。

**建议**：改为

```
存档：
  var snapshots = containerService.SnapshotAll();       // IItemSnapshotSerializer
  saveSystem.Write(json);                               // 落盘属存档子系统
```
