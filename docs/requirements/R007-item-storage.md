# 需求：物品与存储子系统

## 0. 本文档的定位

本文是物品与存储子系统的**正式需求文档**，取代 [2026-11-17 Kickoff 需求](../brainstorms/2026-11-17-item-storage-requirements.md)（该文保留为问题发现记录）。相比 Kickoff 版本，本次修订：

1. **吸收边界分析裁决**：15 项越界需求（网络同步、UI、掉落、商店、合成、词条 roll、耐久规则、货币、地面掉落、容器嵌套、内容包、存档落盘、GAS 重构、编辑器工具）全部归位，不在本文作为 Deferred 含糊保留（见 §六）。
2. **锁定已在设计阶段定稿的结论**：三层数据模型、堆叠形态、索引表设计、整行/快照语义、全量 Carrier 规模决策。
3. **修正评审发现的契约缺口**：`item.slot` 不覆盖无序容器、容器销毁的索引清理由服务层强制、`Destroy` 必须能表达"拒绝非空容器"、定义 provider 必须显式接收表数据源、快照恢复必须可报告失败。
4. **更新事实状态**：Core 的 Trait 反序列化缺陷（A1）代码已修复、待 Unity 验证——它不再是"设计阻塞"，但仍是**存档验收的前置**。
5. **主键体系修订（2026-11-17）**：物品定义键（以及效果引用、词条引用）改为**全局唯一字符串键**，与 R006 的数据包行键一致。理由：物品定义表是 mod/DLC 的主要扩展对象，数字 ID 在多源合并下必然冲突；CarrierId 的架构 ID 重构与 Minecraft 1.13 扁平化（`namespace:path`）是同方向的历史先例。本修订贯穿 RI1、RI3–RI7、RI9、RI16、RI31、RI35–RI37 与全部示例。

> **与 D007 的偏差**：D007 中的 `ItemDefinitionView.Id`（int）、`ItemCoreTrait.DefinitionId`（int）、`ItemRecord.DefinitionId`（int）、`UseEffectId`（int）、`AffixId`（int）与 `CarrierGroupIndex<int>("item.definition")` 全部需改为字符串键（`Key`），`ConfigItemDefinitionProvider` 的取键函数随之改为 `Func<TRow, string>`。此项需在 D007 修订时一并同步。

旧条目对照（R1–R24 → RI1–RI44）：字段级需求保留语义，编号重排以匹配分层结构；`R19` 的"容器批量快照"升级为硬需求（RI37），`R21` 的"事件桥接"保留（RI36）。

## 一、背景

框架与 Demo 当前**没有任何物品相关代码**（全仓库检索 `inventory/item/storage/equip` 无命中），但底层能力已经齐备：

| 现有能力 | 物品系统的对应物 | 缺口 |
|---|---|---|
| `DataCarrier` / `DataTrait` | 物品实例、容器实例 | 无领域载体类型约定、无必需特征定义 |
| `CarrierIndex` / `CarrierGroupIndex`（D005） | 容器 ↔ 物品、槽位 ↔ 物品、定义 ↔ 物品 | 无领域表名约定 |
| `AbstractModel` | 容器/物品全局索引视图 | 无 |
| 事件系统 | 物品变更通知 | 无领域事件 |
| Carrier 序列化 | 存档往返 | 需容器级快照语义（逐载体 JSON 不可用，见 RI37） |
| Luban 配置表 | 物品定义 | `NexusFramework.Config` 尚未落地（见 §七） |

三个必须显式拆开的问题：

1. **定义与实例混用**：模板（静态）与实例（动态）混在一起，会导致配置被运行时改写，或实例数据塞进配置表。
2. **"存储"有两种语义**：**归属存储**（容器里放了什么）与**持久化存储**（存档读写）——数据形态、验收标准完全不同，本文分开定义（§四 C 与 G）。
3. **定义表链路决定是否绑死 GAS**：唯一可用链路是 GAS 私有 `IConfigLoader` + `ConfigModel`；物品必须走 Config（R006），不得引入 GAS 依赖。

---

## 二、目标

1. Emberheart Demo 能跑通一条端到端链：**拾取 → 进背包 → 装备 → 发事件（GAS 侧施效）→ 产出快照 → 读档还原 → 状态一致**，全程无手写 Carrier 遍历或索引清理。
2. 业务代码不出现对 `CarrierManager` 的直接调用（物品相关），全部经物品服务 API。
3. 新增一件物品只需改 Excel + 跑 gen，不改代码；mod 新增物品与本体、其他 mod 的物品**永不冲突**。
4. 核心规则（容量、槽位、堆叠、原子性、索引清理）有 EditMode 测试覆盖；序列化往返有独立测试。

---

## 三、术语

| 术语 | 定义 |
|---|---|
| **物品定义** | 静态配置行，描述"这类物品是什么"：名称 key、图标 key、分类、堆叠上限、耐久上限、标签、效果引用、槽位约束。只读 |
| **定义键**（Definition Key） | 物品定义的全局唯一字符串标识，沿用数据包行键格式：`<packId>:<localKey>`（如 `core:item.potion`、`com.acme:item.elixir`） |
| **物品实例** | 运行时载体，描述"这一个/这一堆物品"：定义键、数量、耐久、词条。可增删改 |
| **容器** | 承载归属关系的载体：背包、仓库、装备栏（地面掉落堆不属本期，见 §六） |
| **槽位** | 容器内的具名位置；装备栏为"固定槽位 + 单物品约束" |
| **归属存储** | 物品实例"在哪个容器的哪个位置"的关系数据 |
| **持久化存储** | 物品与容器状态写入存档、读档还原的能力（本模块只产出快照） |
| **堆叠** | 多个同定义物品共享一个实例，以 `Count` 字段表达 |

## 四、需求

### A. 物品定义（静态配置）

- **RI1.** 物品定义以 Luban 表承载，至少可表达：**全局唯一行键**、名称 key、描述 key、图标 key、分类、堆叠上限、耐久上限、标签、使用效果**键**、可装备槽位类型。
- **RI2.** 不同分类的专属字段（装备 / 消耗品 / 材料）通过 Luban 可选字段或 bean 表达；物品系统**不硬编码**具体字段名，只按统一视图读取通用字段，分类专属字段经 escape hatch 交给业务解释。
- **RI3.** 业务通过 `IItemDefinitionProvider` 访问定义；接口签名**不得暴露 Luban 生成类型**。只读视图至少含：`Key`（`string`）、`NameKey`、`DescriptionKey`、`IconKey`、`Category`、`MaxStack`、`MaxDurability`、`Tags`、`UseEffectKey`（`string`）、`AllowedSlot`，以及指向原始行的 escape hatch（框架内部不读）。**不提供数字定义 ID 作为对外标识**。
- **RI4.** 与 Config 的衔接形态固定为**适配器**：`ConfigItemDefinitionProvider<TRow>(ITableReader<TRow> table, Func<TRow, ItemDefinitionView> map, Func<TRow, string> getKey)`。构造即接收表数据源；表未注册时返回空 provider + 诊断，**不抛异常**。物品核心库对具体行类型零知识，换表或换数据源只改业务层一行。
- **RI5.** 定义中的名称、描述、图标只存**本地化 key / 资源 key**；key 的解析属本地化包与资源包（内容包四元组，未建），物品系统不承担解析职责。三类 key 采用与行键相同的命名空间式格式 `<namespace>:<path>`（如 `core:text.item.potion`、`core:icon.item.potion`，冒号为唯一分隔符），由内容包规范统一治理，物品系统只透传。
- **RI6.** 定义表加载期校验：行键全局唯一、行键的命名空间段为已注册包标识、必要的引用（效果键、槽位类型）可解析；违规必须能定位到表名与键值，**不静默降级**。
- **RI7.** 物品定义表遵循 R006 的数据包约定：表名 `tbitem`、大写 `ID` 字符串行键、含 `is_void` 列、包级命名空间、数据落 `Resources/DataPacks/{packId}/tbitem.json`。

### B. 物品实例

- **RI8.** 物品实例以 `DataCarrier` 承载，具有稳定的载体类型名（供索引与存档识别）。
- **RI9.** 每个实例必须携带且仅携带一个**核心特征**，至少含：**定义键**（`string`）、数量、绑定标记；高频字段（耐久）优先合入核心特征，避免为每个实例多加一个 Trait。缺失核心特征视为非法实例。
- **RI10.** 可堆叠物品以"单实例 + 数量"表达；不可堆叠物品数量恒为 1。堆叠上限来自定义（`MaxStack = 1` 即不可堆叠）。
- **RI11.** 实例可附加可选特征（耐久、词条、自定义数据）；堆叠与非堆叠共用同一套特征模型，**不为两者建立两套载体**。
- **RI12.** 所有物品 Trait 必须满足：无参构造（反序列化重建路径）、字段可被 `JsonUtility` 序列化、禁止 `Dictionary` / 接口 / 多态字段、集合必须为可序列化列表。每个实例的 Trait 数量建议 ≤ 3（Trait 数量直接影响销毁与序列化成本）。
- **RI13.** 实例的创建与销毁必须经服务层 API；业务代码不得绕过 API 直接调用 `CarrierManager`，以保证事件、索引与校验一致。

### C. 容器与归属

- **RI14.** 容器以 `DataCarrier` 承载，携带容器特征：容器类型（无序容量型 / 槽位型）、容量或槽位数、约束标识。
- **RI15.** 支持两类容器语义：**无序容量型**（容量上限 + 物品集合）与**槽位型**（固定槽位 + 槽位 → 物品映射）。装备栏必须是槽位型；背包可按需选择。
- **RI16.** 归属关系由三张约定索引表达，**方向与基数必须正确**：
  | 索引 | 类型 | 方向 | 用途 |
  |---|---|---|---|
  | `"item.container"` | `CarrierGroupIndex<CarrierId>` | 多对一，双向可查 | 容器 → 物品集合；物品 → 所在容器 |
  | `"item.slot"` | `CarrierIndex<ItemLocation>` | 一对一 | 物品 → `(容器, 槽位)`；**仅槽位型容器的物品登记** |
  | `"item.definition"` | `CarrierGroupIndex<string>` | 多对一 | 定义键 → 物品集合；按定义查找与统计 |

  - **禁止**用 `CarrierIndex<CarrierId>` 表达"物品 → 容器"：双射表在值冲突时静默驱逐，多个物品指向同一容器会互相删除；
  - 无序容器的物品**不进** `item.slot`（否则同一容器所有物品的 `ItemLocation` 均为 `{容器, -1}`，同样互相驱逐）；
  - 三张索引的表名为约定，由物品模块的约定常量类单一持有；
  - 定义索引的键是字符串定义键；索引只在实例创建/销毁/定义键变更时维护，不在查询热路径计算字符串。
- **RI17.** 索引条目在物品载体销毁时由 `CarrierManager` 自动清理；但 `item.slot` 的复合值（含 `CarrierId`）**不在自动清理的覆盖范围内**——容器销毁必须经服务层先枚举并解绑该容器的槽位条目。
- **RI18.** 一个物品实例在同一时刻只能属于一个容器；该约束由服务层保证（分组索引不强制多归属），所有跨容器操作必须先解绑旧归属。
- **RI19.** 容器销毁语义必须可表达拒绝：非空容器默认**拒绝销毁**并返回 `ContainerNotEmpty`；显式丢弃内容走 `DestroyWithItems`。实现顺序为：清理槽位索引 → 销毁物品（如需要）→ 销毁容器。
- **RI20.** 容器约束以数据驱动注册（约束标识 + `IContainerConstraint` 注册表）：分类白名单/黑名单、单槽位物品数量、堆叠上限覆盖、槽位类型匹配。新增约束不改核心代码。

### D. 操作与规则

- **RI21.** 提供基础操作：**获得、移除、移动、交换、拆分、合并、销毁、使用**，全部经服务 API 暴露，返回结构化结果（成功 / 失败原因码 / 受影响数量）。
- **RI22.** 原子性：先完成全部校验（容量、槽位、约束、数量、定义存在），再一次性写入；失败**不产生任何中间态**。索引写入顺序必须在实现中显式约束（先探测后绑定；`Swap` 两侧全部预校验通过后才写）。
- **RI23.** 获得：`TryAutoMerge` 为真时先补满同类堆叠再新建；整体放不下时**全部失败**（默认全有全无）；若未来需要部分成功，另开显式 API 并返回实际数量。
- **RI24.** 移除：数量降到 0 时销毁实例并清理两张分组索引；返回的句柄可能已失效，调用方须经 `IsValid` 判断后使用。
- **RI25.** 移动：目标槽位为空时移动；被占时失败（调用方改用交换）；目标为无序容器时**不得**写入 `item.slot`，且原为槽位型时必须解绑原槽位。
- **RI26.** 拆分：源实例数量减少，新实例加入目标位置；带词条物品的复制规则必须显式定义（默认：不可堆叠物品禁止拆分，堆叠物品的词条按数量均分取整）。
- **RI27.** 使用：只扣数量并发送事件，**不执行效果**；效果由 GAS 侧订阅执行。
- **RI28.** 违反容量、槽位、类型、数量约束的请求必须被拒绝，返回可区分的原因码（容器满 / 槽位被占 / 类型不符 / 数量非法 / 定义缺失 / 容器非空等）。

### E. 查询

- **RI29.** 查询**不遍历全部载体**：容器内列举走 `item.container`；按定义查找与统计走 `item.definition`。（依据性能基线：全扫 100 万物品按定义统计约 222 ms，走索引约 28 µs。）
- **RI30.** 查询提供两种形态：**缓冲复用**（写入调用方传入的 `List`，热路径零分配）与**便捷枚举**（冷路径，允许分配）。缓冲复用形态依赖 Core 的分组索引补充 `CopyMembersTo`（见 §七 依赖 G4）。
- **RI31.** 库级统计 `CountHeld(string definitionKey)` 的语义明确为"全库按定义键计数，不含所有权概念"；需要按玩家/归属统计时由调用方显式传入容器集合。

### F. 事件

- **RI32.** 所有改变状态的操作成功后发送**类型化 struct 事件**；事件只携带最小必要上下文（容器、物品、定义键、变更前后数量/槽位），不携带完整快照；订阅方按需经查询接口读取。
- **RI33.** 事件集至少覆盖：物品获得、物品移除、物品移动、数量变化、装备、卸下、使用、拆分、合并、容器变化。其中容器变化事件为可选（避免与物品事件重复广播）。
- **RI34.** 高频搬运（传送带、机械臂、批量整理）场景必须支持**帧末合并/批量事件**，避免每帧数千次广播；核心先提供单事件，批量事件作为可选能力。
- **RI35.** 装备 / 卸下由"移动到槽位型容器"触发，发 `ItemEquippedEvent` / `ItemUnequippedEvent`；事件携带定义键而非数字 ID。物品模块**不引用 GAS 类型、不直接调用 GAS API**。

### G. 持久化（只产出快照）

- **RI36.** 物品存档采用**容器批量快照**（`ContainerSnapshot` + `ItemRecord[]`），**不使用** `CarrierManager.SaveToFile` 的逐载体 JSON。依据：逐物品 137 B/件、100 万件约 10.2 s；容器批量 35 B/件、约 0.95 s。
- **RI37.** 快照必须带 `SchemaVersion`（当前 1）；旧档缺少新增字段时按默认值读取。**版本迁移的执行归存档子系统**，物品模块只声明当前版本与字段兼容约束。
- **RI38.** 快照恢复必须能报告失败（返回结果/诊断），不得静默丢弃或部分恢复后假装成功。
- **RI39.** 落盘、槽位、加密、存档目录管理等**不属于本模块**；物品模块只负责序列化结构与还原。
- **RI40.** 物品 Trait 的无参构造要求（RI12）与 Core 的 Trait 重建路径配套：A1 修复后仍以 `Activator.CreateInstance` 为主路径，`GetUninitializedObject` 仅为兜底。
- **RI41.** 快照中的定义键以**完整字符串**存储（不做运行时编号压缩）：读档不依赖任何运行时分配顺序，跨版本、跨包加载顺序稳定。其对存档体积的影响须实测（见 RI44）。

### H. 扩展性与规模

- **RI42.** 新增容器类型、约束策略、可选特征结构不修改物品核心代码（开放封闭）。新增物品分类 / 槽位类型属**破坏性变更**（枚举在接口层），需显式版本说明；但新增**物品定义**只需新增行键，不涉代码。
- **RI43.** 采用**全量 Carrier**，不做冷热分离，目标上限约 **50 万**物品实例。超过上限时通过新增存储后端（`IItemStorage`）扩展，核心 API 不变。字符串定义键带来的每实例内存增量需实测后重新确认上限。
- **RI44.** 字符串键的成本必须验证并记录：定义字典（≥1 万行）的加载与查询耗时、每实例定义键的内存占用、快照体积增量，并与数字键基线对比。若超出预算，可评估"内部数字代理 + 外部字符串键"的优化，但对外契约不变。

## 五、验收标准与性能边界

### 验收标准

1. **端到端链**：拾取 → 背包 → 装备 → 事件 → 快照 → 读档还原，状态完全一致。
2. **无直连**：业务代码中（物品相关）不出现 `CarrierManager` 调用。
3. **测试覆盖**：容量/槽位/堆叠/原子性/索引清理有 EditMode 测试；序列化往返有独立测试；容器销毁不留悬垂索引条目。
4. **数据驱动**：新增一件物品只需改 Excel + 跑 gen。
5. **无冲突**：本体与任意 mod 同时定义"本地同号"物品时，两件物品共存且互不覆盖。

### 验收示例

- **AE1. 堆叠（RI10, RI21, RI23）**：背包有 3 个 `core:item.potion`（`MaxStack = 5`），再获得 4 个同键物品 → 结果为一个数量 5 的实例 + 一个数量 2 的实例，总数为 7，无实例超上限。
- **AE2. 容量拒绝（RI15, RI22, RI28）**：容量 10 的背包已有 10 件不可堆叠物品，再添加 1 件 → 失败并返回"容器满"，背包状态不变。
- **AE3. 拆分（RI26）**：数量 5 的堆叠拆出 2 个 → 原实例 3、新实例 2，定义键一致；带词条的复制规则按约定执行。
- **AE4. 跨容器原子性（RI18, RI22）**：物品从背包 1 移向已满的背包 2 → 两侧均不变，返回失败原因。
- **AE5. 装备槽（RI15, RI20, RI35）**：装备槽只接受"武器"分类；放入药水被拒绝；放入武器成功后可反查槽位，卸下后槽位索引条目消失并发送对应事件。
- **AE6. 快照往返（RI36–RI41）**：两个容器（容量型 + 槽位型）与若干堆叠/非堆叠实例，序列化 → 清空 → 反序列化后，内容、数量、槽位映射、可选特征与之前完全一致；旧版本档（缺新字段）读取成功并取默认值；读档后定义键仍能解析到定义（不依赖包加载顺序）。
- **AE7. 容器销毁（RI17, RI19）**：非空容器 `Destroy` → 拒绝；`DestroyWithItems` → 容器与其物品的 `item.container`、`item.slot`、`item.definition` 条目全部消失，无悬垂条目，`TryGetCarrier(旧位置)` 返回 false。
- **AE8. 多源定义（RI6, RI7）**：本体包提供 `core:item.potion`，mod 提供 `com.acme:item.potion`（同本地名、不同命名空间）→ 两个定义共存，`All` 同时返回两者，实例分别引用各自键；mod 用 `core:item.potion` 键覆盖时按数据包规则整行替换。

### 性能边界

| 维度 | 安全区 | 警戒区 | 不可用 |
|---|---|---|---|
| 物品实例总量（PC） | ≤ 20 万 | 50 万 | 100 万 |
| 单容器物品数（UI 读取） | ≤ 500 | 1 000 | 5 000 |
| 每帧搬运次数 | ≤ 5 000 | 10 000 | 20 000 |
| 每帧生成 + 销毁 | ≤ 2 000 | 5 000 | 10 000 |
| 全量存档方式 | 容器批量快照 | 二进制快照 | 逐物品 JSON（> 1 万） |

规模代价（全量 Carrier，2026-11-17 决策）：10 万 ≈ 85 MB / 冷构建 2 s；20 万 ≈ 170 MB / 4 s；50 万 ≈ 425 MB / 10 s；100 万 ≈ 850 MB / 19 s 且进入 Mono 风险区。**真正的硬约束是内存**。上表基于数字定义 ID 的基线；改为字符串键后的内存增量待 RI44 实测。

## 八、问题状态

### 已决策（来自 Kickoff Q1–Q8、设计评审与 2026-11-17 主键修订）

| 问题 | 结论 |
|---|---|
| Q1 "存储"范围 | **两者都要**：归属存储（本期核心）+ 持久化快照（本期交付结构，不落盘） |
| Q2 实例粒度 | **堆叠 = 单 Carrier + 数量**；需要逐件独立数据的物品归为不可堆叠 |
| Q3 系统归属 | 程序集名与命名空间为 `NexusFramework.Inventory`（物理位置待定，不影响契约）；适配器与核心同库，接受对 Config 的硬引用；**对外契约部分进入 R006 定义的契约包**（见 G13） |
| Q4 定义表链路 | **走 Config（R006）适配器**（RI4）；Config 未落地期间允许内存实现，接口不变 |
| Q5 GAS 桥接 | 本期只做**事件桥接**（基础事件 + 装备/使用事件），属性与效果执行在 GAS 侧 |
| Q6 标签 | 定义存**命名空间化字符串标签 key**；GAS 侧提供可选匹配器 |
| Q7 容器强弱约束 | 本期只实现"槽位型（装备栏）+ 容量型（背包）"两种，不支持同容器混合语义 |
| Q8 使用物品 | 做**最小版本**：扣数量 + 发事件，不执行效果 |
| **Q9 主键体系** | **字符串全局键**（`<packId>:<localKey>`）：定义键、效果键、词条键、标签 key、资源/本地化 key 一律命名空间化；不使用数字 ID 作为跨包标识 |

### 未决（不阻塞需求定稿，需规划/设计阶段确认）

- 物理目录位置（`Assets/NexusFramework.Inventory/` vs `Assets/Demo/Emberheart/`）。
- 词条拆分复制规则的具体取值（RI26 的默认规则需业务确认）。
- 存档版本号的具体格式与迁移函数注册方式（与存档子系统对齐）。
- 物品定义表的列设计（单表宽行 vs 主表 + 分类子表 vs bean 多态）。
- 查询 API 的返回形态组合（缓冲 + 枚举的具体签名）与性能预算的落地验证。
- 事件粒度是否拆到"每操作一事件"之外再分类型事件。
- 是否需要物品定义缓存（Model 层）及失效策略。
- `CopyMembersTo`（G4）的排期：若不补，RI30 降级为"一次分配"。
- **GAS effect key 的命名空间化方案**（G10）：由 GAS 提供字符串键，还是由业务维护映射表。
- 字符串定义键在快照与索引中的具体编码（完整键 vs 短哈希 + 键表），以 RI44 实测结果为准。
- Luban `string` index 的可行性（R006 D5 / 验证文档 V2）：若回退为 `TableModel` 自建字符串字典，物品侧的 `IItemDefinitionProvider` 与索引签名均不受影响。
